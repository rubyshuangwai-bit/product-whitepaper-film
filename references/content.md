# 资料提炼与口播

## 先找到能支持宣传的证据

读取用户指定的白皮书、手册和 PPT，保留原件；截图可从用户材料提取，不自动覆盖原文件。长文档先建立章节索引，再精读产品定位、核心功能、限制、部署/配置、典型使用流程及相关图。图注和功能描述必须一起核对。

每个来源包含 `id / path或url / title`；每个事实包含 `id / text / source_ids / locator / status`。`locator` 使用真实页码、章节或用户消息摘要；无法定位就标待核实，不编页码。`status` 为 supported（资料支持）、planned（规划）、unverified（未确认）。supported 是对来源支持程度的记录，不是独立实机测试结论。

白皮书与手册有冲突时检查日期、版本和用户最新纠正；用户明确忽略版本号通常指宣传文案，不意味着可混用相互冲突的能力。关键冲突影响稿件时收敛为一次问题，继续处理其他段落。

## 形成一条产品主线

先给出一句定位、目标受众、希望记住的两三个信息，以及每项可用证据。客户介绍通常强调产品价值与部署/使用方式；技术交流可以增加结构层次；朋友圈短片应缩短术语链。顺序和长度随内容调整，不固定五幕和15秒。

稿件避免把“平台提供基础能力”说成“平台直接实现所有上层体验”，也避免把某一种适配路径推广为所有芯片通用做法。图片只显示某配置界面时，不以它证明另一种部署已实测。

示例：虚构资料写“支持关键词查找和原文查看”。可提炼成“查找资料并核对出处”；不能加“零延迟”“支持全部格式”或没有证据的准确率。

类别型生态介绍：已有清单可作为事实依据，但镜头优先展示模型类别、框架层和硬件类别；品牌与型号只在用户需要且已核实支持范围时出现。不要用一屏不可读的 logo 墙表示“生态丰富”。

## 对齐的最小产物

提供完整口播和对应画面构想，标出少量真正影响内容的待确认项。用户已接受的主线直接沿用。记录确认的具体范围：稿件、某张截图、音色、单镜、整片各自独立。不要把一次“可以”无限外推。
